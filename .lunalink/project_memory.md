# LunaLink 项目强行记忆

> 这个文件不是 App 功能需求文档，而是约束 LunaLink Agent 在当前项目内协作行为的项目记忆。
> 后续 Code 模式任务开始前，必须先读取本文件；未读取时，不得声称已遵守项目记忆。

## 0. 生效前提

- 只有当本文件内容进入当前对话上下文后，规则才会真正约束 Agent。
- 如果 App/系统没有自动注入本文件，用户应在任务开头明确要求：`先读取 .lunalink/project_memory.md，并严格遵守。`
- Agent 不能把“文件存在”误认为“已经读取并生效”。

## 1. 每次 Code 任务开始必须执行

1. 先读取 `.lunalink/project_memory.md`。
2. 读取后先确认：`已读取项目记忆`。
3. 再输出 todo 并执行工具/文件操作。
4. 如果当前模式禁止工具调用，必须说明当前无法读取文件，不能假装已读取。
5. 如果没有读取本文件，不得声称已经遵守项目记忆。

## 2. 项目记忆的含义

- 用户说“项目记忆”“强制记忆”“你记住”“写进项目里”“防止你犯错”“每次行动后自检”，默认是约束 Agent 行为。
- 默认不是让当前 Flutter App 新增功能。
- 除非用户明确说“把项目记忆功能做进 App/软件/页面里”，否则禁止擅自转成软件开发需求。

## 3. 当前项目强制规则

- 行动前必须判断当前是 MTC 还是 Code。
- MTC 模式：禁止工具调用、禁止 `<todo>`、禁止 `<file_change>`，只能沟通需求/方案/风险/UI。
- Code 模式：复杂任务必须先规划 todo，再持续执行工具，todo 未全部 done 前不能停。
- 当前开发环境为 Local 时，优先使用本地工作区工具。
- 不得把工具调用成功当成任务完成。
- 不得把源码写入当成构建完成。
- 不得把 workflow 触发成功当成 APK 构建成功。
- 用户要 APK/链接/下载时，必须确认 run completed + conclusion success + artifact 存在，并给 Actions 页面或可用下载入口。
- 若发生错误，必须复盘：错误、原因、正确做法、以后必须。

## 4. 行动前自检清单

每次行动前必须检查：

1. 当前模式是否允许工具调用？
2. 用户是在让我改软件，还是让我遵守/记录 Agent 行为规则？
3. 是否需要先读取项目记忆？
4. 是否存在歧义需要澄清？
5. 是否可能把中间步骤误判为最终完成？

## 5. 行动后自检清单

每次工具结果或阶段完成后必须检查：

1. 工具是否真的成功？
2. 用户最终目标是否已达成？
3. 是否还需要继续下一步？
4. 是否需要验证文件、构建、artifact 或链接？
5. 是否犯了旧错误？如果是，必须写入复盘。

## 6. 已知错误复盘

### 错误：把项目记忆误解为 App 功能

错误：用户要求“加项目记忆/防止你犯错”，Agent 开始读取 Flutter 项目并准备给 App 新增功能。

原因：没有先判断“项目记忆”是 Agent 行为约束还是产品功能。

正确做法：默认理解为当前项目协作规则，先记录并遵守，不擅自改 App。

以后必须：看到“项目记忆/你记住/防止犯错/自检”时，优先作为 Agent 行为规则处理。

### 错误：把项目记忆机制又解释成 App 层实现

错误：用户强调不是 App 后，Agent 又解释 App 自动注入/页面/服务等实现。

原因：没有牢牢记住用户当前讨论的是“Agent 在项目里如何遵守”，不是产品需求。

正确做法：只讨论和执行当前项目记忆文件与工作流，不转成软件功能。

以后必须：除非用户明确要求开发功能，否则不讲 App 层实现。

### 错误：文件存在但未读取却声称会遵守

错误：之前把“写进项目文件”当成“后续一定会遵守”。

原因：没有区分文件持久化和上下文生效。

正确做法：每次任务开始必须读取本文件；没有读取就不能说已遵守。

以后必须：在 Code 模式下，若用户要求遵守项目记忆，第一步读取 `.lunalink/project_memory.md`。

### 错误：未确认现有版本就把 App 版本降级

错误：用户实际当前版本已经是 `1.2.9`，Agent 只依据本地/旧上下文中的 `1.2.6+1002`，把版本错误改成 `1.2.7+1003`，导致相对用户当前版本反而降级。

原因：没有先向 GitHub/当前发布状态/用户声明版本进行交叉确认，也没有遵守“升级必须高于用户当前已安装版本”的原则；把看到的旧文件版本误判为真实当前最高版本。

正确做法：修改 Android/Flutter 版本号前，必须先确认用户当前已安装版本或仓库/构建中的最高版本；新版本的 `versionName` 和尤其 `versionCode` 必须严格大于当前已安装版本。若用户明确说明当前版本，例如 `1.2.9`，则目标版本必须高于它，例如 `1.2.10+1010`。

以后必须：涉及 APK 更新、版本相同、版本升级、安装覆盖时，不允许只看单个文件就改版本；必须先判断是否会降级，并使用严格递增的 `versionCode`。如果不确定当前最高 `versionCode`，要选择明显更高的编号，不能降低。

### 错误：优化过程中把原本已有的控制台入口/UI 弄没

错误：App 原本已有控制台/日志能力，后续 UI/功能优化时没有把控制台当成必须保留的核心功能，导致用户找不到控制台或控制台入口失效。

原因：修改聊天页、图片生成页和顶部入口时，没有先列出现有核心功能清单，也没有做“控制台入口、日志写入、复制/清空日志”的回归验证。

正确做法：任何涉及 HomeScreen、请求流程、图片生成流程、设置入口、历史入口、顶部 AppBar 或底部弹窗的改动，都必须先确认现有控制台服务和入口是否存在；如果需要重构 UI，必须迁移控制台入口，而不是删除或隐藏。

以后必须：控制台、请求日志、错误日志、request id、复制日志、清空日志属于核心调试能力；优化 UI 或功能后必须验证控制台仍能打开，发送请求和失败异常仍会写入控制台。
